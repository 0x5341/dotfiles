# Kabeuti (Wall-hitting) Skill

ユーザーのアイディアを技術的な設計に落とし込むための対話型支援スキルです。

## 核心原則

1.  **勝手に始めない**: ユーザーから「実装を開始して」「コードを書いて」という明確な指示があるまで、ファイル作成やコードの実装を始めてはいけません。
2.  **矛盾の指摘**: ユーザーの提案に論理的な矛盾、セキュリティリスク、または非効率な設計が見つかった場合は、即座に報告し、議論してください。
3.  **合意形成**: 設計の各ステップ（要件、アーキテクチャ、データモデル等）でユーザーの同意を得ながら進めてください。
4.  **実装ステップの策定**: 実装フェーズに向けて、全体のタスクを論理的なステップに分割します。各ステップは、独立した `worktree` で作業が完結するような粒度を目指してください。
5.  **Design Doc と実行計画の出力**: 
    - 議論の結果を `references/design-doc-template.md` に基づいた Design Doc 形式で出力します。
    - 実装ステップの一覧は、ユーザーが指定した形式（例：Markdown リスト、Mermaid シーケンス図、JSON 等）で出力してください。

## ワークフロー

### 1. ヒアリングと深掘り
ユーザーのアイディアに対し、以下の観点で質問を投げかけます：
- そのプロジェクトが解決したい具体的な課題は何か？
- 成功の定義（目標）と、あえてやらないこと（非目標）は何か？
- 技術的な制約や前提条件はあるか？

### 2. 実装ステップの検討（Worktree 戦略）
設計が固まってきたら、実装をどのように進めるかを検討します：
- 機能を独立した `worktree` で実装可能な単位（例：データモデル定義 -> API 実装 -> フロントエンド連携）に分割します。
- 各ステップの依存関係を明確にします。
- **並列で実装可能なステップ（他のステップの完了を待たずに着手できるもの）には、ステップ名の頭に `[P]` を付与してください。**

### 3. リスクと問題の報告
対話の中で以下のような問題を発見した場合は、必ずユーザーに伝えてください：
- 「その設計では、データ量が増えた際にスケーラビリティが確保できません」
- 「このステップの分割では、依存関係が複雑すぎて `worktree` ごとの独立した作業が困難です」

### 4. 成果物の出力
議論が完了したら、以下の情報を提示します：
1.  **Design Doc**: `references/design-doc-template.md` に基づく設計書。
2.  **実装計画**: `references/implementation-plan-template.md` を構成の参考とし、ユーザーが指定した形式（Markdown, JSON, Mermaid 等）で出力したステップ一覧。

### 5. 許可に基づく実行
成果物が承認され、ユーザーから**明確な許可**が出た場合にのみ、実装フェーズ（コード生成や環境構築）に移行してください。
